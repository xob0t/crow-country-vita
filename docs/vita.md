# PS Vita

The app is Unity's own PS Vita player, built by the Unity 2018.2.19f1 editor with its PS Vita module and Sony's PS Vita SDK 3.570 ([build.md](build.md) sets them up). The build is a PC Hosted player in `builds/crow-2018.2.19f1-vita`; `pipeline.py package` turns it into `builds/crow-2018.2.19f1-vita.vpk` with the player as `eboot.bin`, its trial flag cleared, and LiveArea art made from the game's Steam store images (`livearea.py`). The title ID is `CROW00001`.

## Installing

You need a PS Vita on HENkaku or Ensō with [VitaShell](https://github.com/TheOfficialFloW/VitaShell). [vitacompanion](https://github.com/devnoname120/vitacompanion) is optional: it adds an FTP server that works while the game runs and a command server that `vita.py` uses to start and quit the game, take screenshots and press buttons.

1. Copy the VPK to the console: in VitaShell press Select to start its FTP server, and upload the VPK to `ux0:data/` with any FTP client (port 1337), or copy it over USB.
2. In VitaShell, open the VPK and install it.

The app asks for the +109 MB memory expansion (`DowngradeBuild.cs`), which the system reads from `param.sfo` at installation. A build that changes `param.sfo` needs a new installation; anything else can be updated in place with `vita.py sync`.

On the console the app keeps its files in:

| Folder | What |
| --- | --- |
| `ux0:app/CROW00001` | The installed app. |
| `ux0:data/CrowCountry` | The game's saves and settings (`compat/Saves.cs`). The app's own folder is read-only. |
| `ux0:data/crow` | The probe's flags (`args.txt`) and the player's log (`log.txt`, at most 8 MB; the two runs before in `log.prev.txt` and `log.prev2.txt`). |

## vita.py

`tools/downgrade/vita.py` drives the installed app at `CROW_VITA_HOST` (or `DRIFTER_VITA_HOST`); `uv run tools/setup.py --vita-host <address>` sets it. `sync`, `log`, `args`, `files` and `crashes` need only an FTP server on port 1337, VitaShell's or vitacompanion's; `seed` needs no console. The others need vitacompanion's command server on port 1338: `do`, `install` and `shot` need vitacompanion 1.20 or later, `perf` 1.33. `install`, `perf` and `shot` use commands the released vitacompanion lacks; without them they stop with a message.

```powershell
uv run tools/downgrade/vita.py sync              # upload what changed since the last sync (the first uploads everything)
uv run tools/downgrade/vita.py run               # quit, sync, launch
uv run tools/downgrade/vita.py log --tail 40     # the player's log
uv run tools/downgrade/vita.py args -crow-heartbeat 5   # the probe's flags for the next launch; no flags clears them
uv run tools/downgrade/vita.py args --show       # the flags the next launch gets, changing nothing
uv run tools/downgrade/vita.py crashes --pull    # the newest crash dump, symbolized
```

| Command | Effect |
| --- | --- |
| `sync [--build dir]` | Upload the files that changed since the last sync into `ux0:app/CROW00001`. |
| `seed --build dir` | Record a build as installed (from its VPK, say) without uploading, so the next sync sends only differences. |
| `install [--build dir]` | Package the build as a VPK and stream it to the installer; also applies `param.sfo` changes. |
| `launch`, `quit`, `run` | Start the game, quit all apps, or quit, sync and launch. |
| `do "<chain>"` | Run a vitacompanion command chain, for example `do "press cross; wait 100ms; release cross"`. |
| `shot [out.png]` | A system screenshot of what the screen shows. |
| `perf` | Clocks, CPU load per core, frame rate and battery. |
| `log [--tail N] [--prev [N]]` | Print the player's log; `--prev` the run before's (`log.prev.txt`), `--prev 2` the one before that. |
| `args [flags...]`, `args --show` | Write the probe's flags to `ux0:data/crow/args.txt` (a value with spaces, such as `-crow-fight-area "Ocean Kingdom"`, is quoted in the file); `--show` prints the file and changes nothing. A word with two dashes is refused, not written as a flag. |
| `files [folder]` | List the files under a console folder, by default the saves. |
| `crashes [--pull] [--thread NAME] [--dump FILE]` | List the crash dumps in `ux0:data`; `--pull` fetches the newest into `artifacts/vita/` and prints a thread's symbolized call chain; `--dump` reads a dump already on the PC. |
| `reboot` | Reboot the console. |

`--build` takes another build folder, such as a test build's `builds/crow-2018.2.19f1-vita-scenes`.

When several jobs share the console, take the `vita-device` lock first (`tools/downgrade/lock.py`); a person at the console holds it as `user: <purpose>`. The commands that change the console (`sync`, `install`, `launch`, `quit`, `run`, `do`, `reboot`, `args`) refuse while someone else holds it: run them inside `lock.py run vita-device ...`, or with `CROW_HOLDER=<your holder name>` after `lock.py take`.

`sync`, `install` and `seed`, and `run` before it quits the game, read the build folder under the `vita-build` lock, so a `build` or `quickcode` can't rewrite the files while they go out (a sync during a quickcode could send the new module with the old metadata, and the game crashed at launch). They hold it as a reader: a vita-build job (a build, a quickcode, `lock.py wait vita-build`) waits for them as for any holder, but a PC build under `pc-build` neither waits for them nor holds them up, so `pipeline.py` stops a PS Vita `build`, `package` or `quickcode` run under `pc-build` (22 Oct): those need `vita-build`. They wait up to `--build-wait` seconds (900 by default) for a build that holds it, then stop with exit 75; `run` waits before it quits the game, so a busy lock leaves the game running. Inside `lock.py run vita-build ...` (also with a `lock.py run vita-device` inside it), or with `CROW_HOLDER` naming the holder of a `lock.py take vita-build`, the lock is the caller's and they don't wait: without `CROW_HOLDER`, a vita-build you took by hand makes them wait for your own lock.

Don't kill `vita.py` while it sends or reads a file: an FTP transfer cut off mid-way can leave the console's FTP server hung until the console reboots. Ctrl+C or Ctrl+Break lets the file in progress finish and then stops; a second one ends the transfer at once by closing its connection cleanly (`lock.py run` waits for its command after Ctrl+C rather than killing it). `sync` and `args` write each file as `<name>.part` and rename it into place, so an interrupted upload never leaves the app a file cut short, and `sync` sends a file it was interrupted on again next time.

Unattended runs need the display kept on. vitacompanion's `nosleep` holds off standby but not the display's idle timeout, and when the display goes off the system pauses the game: `perf` shows `app: none` and 0 fps, while FTP and the command server still answer. `screen on` resumes the game where it was (its clock leaves the pause out), but a script that reads the log, finds it stalled and quits the game ends the log with no dump, which looks like a silent death (render r3's Pool and r4's Roadside on 17 Oct). `vita.py log` therefore sends `nosleep on; screen on` with every read, and `shot` waits until the screen draws again after waking it (it used to save a black frame). A script that polls the console another way should repeat `vita.py do "nosleep on; screen on"` every few seconds, as `fightbench.py` does. Never send `screen off`: with `nosleep off` the console goes into full standby, and only its power button brings it back.

## Probe flags

CrowCompat, the compatibility library the pipeline adds to the game, has a measurement probe that is off unless the player gets a `-crow-*` flag. A Windows player takes the flags on its command line; on the PS Vita, which passes no command line, the player reads them from `ux0:data/crow/args.txt`, which `vita.py args` writes. They apply from the next launch. `-crow-help` logs the list of Diag's own flags (scenes, heartbeat, timed runs, screenshots, stall dumps).

## Fight benchmark

`tools/downgrade/fightbench.py` runs the scripted fight (`-crow-fight`, `compat/Fight.cs`) and prints where the frame goes. One command per target:

```powershell
uv run tools/downgrade/fightbench.py vita --modes real,stress --runs 3   # the console: lock, sync, runs, table
uv run tools/downgrade/fightbench.py pc --modes real,stress --runs 1     # a Windows player (run_player.py)
uv run tools/downgrade/fightbench.py pc --vitalike --timeout 1200         # the same at Vita-like CPU speed
uv run tools/downgrade/fightbench.py report <tag>                        # the table again from saved logs
```

`vita` takes the `vita-device` lock (waiting up to `--wait` seconds for whoever holds it, by default not at all; inside `lock.py run vita-device` it uses that), syncs the build (`--no-sync` skips it), and for each mode and run quits the game, writes args.txt, launches, keeps the console awake, waits for the summary line (`--timeout`, 420 s a run), pulls the log and samples vitacompanion's `perf` during the first windows. However it ends, it quits the game and clears args.txt. Each run takes about 3 minutes (about a minute to the title and the area, 12 s of settling, 6 s of fighting, 60 s measured). `pc` runs a copy of the Windows player (`builds/crow-2018.2.19f1`, or `--build`) through `run_player.py`, on its own desktop, windowed and muted; for a Mono build the copy gets today's CrowCompat (compiled into `work/fightbench/compat`), so no new build is needed, and Steam's `steam_api` library and `steam_appid.txt` are left out of it. `--vitalike [CAP]` runs that player at CAP percent of the wall time (5.5 by default) on three cores, with `vitalike.py`'s duty cycle and guards; the calibration was made for the IL2CPP player, so with a Mono build the numbers are only a rough guide. Extra `-crow-*` flags go after `--`, such as `-crow-fight-area "Ocean Kingdom"` or `-crow-shot 40 <png>`.

Logs, perf samples and `summary.txt` go to `artifacts/fightbench/<tag>/` (the tag defaults to the date and time). The table has one row per run and a mean per mode; its columns are milliseconds per frame:

| Column | What |
| --- | --- |
| frame, p50, p95, p99, worst, fps | Frame time (`Time.unscaledDeltaTime`) over the measured windows. |
| main | The main thread's own run time per frame (PS Vita, from the kernel through CrowClock); the rest of the frame it waits for the render thread, the GPU or the display. |
| scripts, phys, anim, skin, part, audio, render, ui, wait | The player loop by subsystem (`-crow-loop-profile`'s steps): every script's Update, LateUpdate and FixedUpdate (PlayMaker's FSMs among them); physics; Animator, Director and legacy animation; skinned meshes; particle systems; audio; culling, draw submission and the renderers' update (this step also waits when the render thread or the GPU is behind); canvases; present, frame start and target-rate waits. The window lines' `top=` lists the costliest steps by name, and each window's CROW_LOOP and CROW_CAMS lines (`cycle=fight-wN`) have the per-step and per-camera detail. |
| gc, gcms, KB/s | Collections, their pause (`-crow-gc-log`) and the allocation rate (IL2CPP players). |
| steps, rate | Physics steps a frame; game time per wall-clock second (under 1 when `-crow-physics-cap` clamps slow frames). |
| alive, shots, kills, hits, shotk, freeMB | Enemies alive (mean), shots fired, kills (the `Kills` global), health drops by shots, kills by shots (not the fight's own), the lowest free main memory (PS Vita). |

The modes. `real` runs Station Square's own fight: its 9 enemies (6 Blobs, 2 Grinners, a Spindle) are those of a later visit (`VisitedCrowCountry`, items 2, 5 and 9, `NPC6` 3, set before the area loads), and 7 of them stand within 5 m of the spot by the area's entry; as they die the fight winds down (about 3 left, out of reach, by the last window). `stress` adds 12 copies of them in a ring around Mara and keeps about 20 alive. `idle` is the same setup with no enemies and no shots, the baseline. Enemies cull themselves beyond 5 m of the camera's visibility point, so only those near Mara cost anything. Mara's spot is fixed per area (`Areas` in `Fight.cs`; elsewhere near the biggest group, or `-crow-fight-spot`), and UnityEngine.Random is seeded, but the enemies' physics and the moment of each frame differ between runs: compare means over several runs. Other areas with many enemies (`-crow-fight-area`): Ocean Kingdom (12 with its globals), Haunted Hilltop (10), Underground SW and Pre Machine Centre (6-7 on a first visit).

## Crash dumps

When the player crashes, the console writes a dump to `ux0:data`. `vita.py crashes` lists them, and `vita.py crashes --pull` fetches the newest, reads it with [vita-parse-core](https://github.com/xyzz/vita-parse-core) (downloaded into `tools/external` on first use) and prints the crashed thread's call chain, with names from the SDK's `psp2bin` and the build's `SymbolFiles`. `sync`, `install` and `seed` keep a copy of the game module's symbols for each build they send (`artifacts/vita/symbols/<fingerprint>`, the last 5, about 55 MB each), and `crashes` uses the copy whose fingerprint the dump lists, so a dump still reads right after the next `quickcode`. Without a copy it maps the dump's game addresses onto the build's symbols through the two modules' exception indexes, which the dump keeps (frames marked `game~`); the engine's frames are always right. `--thread main` prints the main thread instead.

A frame that takes seconds or minutes doesn't crash, and the console has no sampling profiler. `-crow-stall-dump 15` makes the player crash when a frame has taken 15 seconds, so the dump holds the main thread's stack in the middle of it; `-crow-stall-after <t>` skips the stalls of the first t seconds. The watcher looks every quarter of the limit, so a fraction of a second works too (`-crow-stall-dump 0.1` samples a 150 ms hitch).

```powershell
uv run tools/downgrade/vita.py args -crow-stall-dump 15
uv run tools/downgrade/vita.py launch
uv run tools/downgrade/vita.py crashes --pull --thread main
```

## IL2CPP settings

The player's code is compiled as the PS Vita module has it, checked on 16 October (the build log's IL2CPP command line, `UnityEditor.PSP2.Extensions.dll` and `PSP2Il2CppPlugin.dll`):

| Setting | Value |
| --- | --- |
| IL2CPP configuration | `--configuration=Release`. The PSP2 toolchain (SNC) distinguishes only Debug (`-O0 -g`, `IL2CPP_DEBUG`); Master would compile the same, and 2018.2 has no player setting for it. |
| C++ compiler | `psp2snc -O3 -Xthumb=1 -Xc+=exceptions -Xstd=cpp11 -fno-strict-overflow`, `NDEBUG`. -O3 is SNC's highest level; SNC has no link-time optimization, so no call between IL2CPP's C++ files (each assembly is split into `Bulk_*.cpp` files) is inlined: every property getter, `List<T>.Count` and the like is a real call. Thumb-2 keeps the 55-58 MB module small; ARM code would cost memory. C++ exceptions carry managed ones. |
| Linker | `psp2ld --strip-unused-data --strip-duplicates`. |
| Development build, script debugging | Off (`pipeline.py build --development` for the development player). |
| Null and array bounds checks | On (`--emit-null-checks --enable-array-bounds-check`, `DowngradeBuild.cs`; the module's own call leaves them out, Script Optimization Level "fast but no exceptions"), so a null reference or bad index the PC game logs as an exception does not crash the console. Measured without them (same code, a scratch compile): Station Square's real fight, main thread 46.7 -> 46.3 ms, scripts 17.1 -> 16.2 (3 runs each, run-to-run noise about 4 ms); idle 25.3 -> 25.4 (scripts 9.1 -> 8.7); standing 26.4 -> 25.4; the module 57.6 -> 55.0 MB. Under 1 ms of scripts, against crashes where the game throws (DOTween's safe mode catches its targets' NullReferenceExceptions in every area): kept. `Il2CppSetOptionAttribute` (which IL2CPP 2018.2 honours per method and type) could drop them where nothing can be null. |
| Stack traces | Native (no per-method stack trace sentries on the PS Vita); every log type with ScriptOnly stack traces. The game logs about one line a minute in play, so this costs nothing in frames. |
| Graphics jobs | On (`CROW_GFX_JOBS=off` turns them off). `CROW_GFX_JOBS=on`, the default, makes `pipeline.py build` and `quickcode` write `gfx-enable-gfx-jobs=1` into `Media/boot.config` (the 2018.2 PS Vita editor has no setting for it; the player reads it at start), and the camera's draws are then recorded in Unity's two job workers beside the render thread: Station Square, main thread, standing without vsync 24.9 -> 22.1 ms, steady real fight 59.1 -> 55.2. With it on, the user's game crashed on the render thread during an area change (Roadside -> Entrance, 17 minutes into play; `GfxDeviceGXM::DrawBuffers` while the main thread destroyed Roadside's objects); 41 changes in a loop with it on did not repeat it, with or without the gap's drain, nor did a 40-minute soak of 41 changes over seven areas on 18 Oct so they are on again for the user's play-test. |
| Stripping | UnityLinker on every assembly but those `link.xml` keeps whole (the game's, `PLATFORM_LINKED` leaves seven plugins to it); `stripEngineCode` does not apply (the PS Vita player is prebuilt). |

## Code changes without a full build

A full PS Vita build takes `project` and the editor's `build` (about half an hour). For a change to the rewriter or CrowCompat, `quickcode` rewrites the assemblies and replays the last full build's UnityLinker and IL2CPP steps on the inputs that build saved in `work/vita-code-stage`, then puts the new `il2CppAssemblies.suprx` and `global-metadata.dat` in `builds/crow-2018.2.19f1-vita`, in about 2 minutes. `vita.py sync` uploads the two files.

```powershell
uv run tools/downgrade/lock.py run vita-build "me: what for" --wait 1800 -- uv run tools/downgrade/pipeline.py quickcode
uv run tools/downgrade/vita.py run
uv run tools/downgrade/vita.py log --tail 40
```

The time `lock.py` waits for a lock counts against whatever limits the caller's own run (an agent's background command stopped at 2 hours stops `lock.py` and its command with it, in the middle of a build or a console transfer), so keep `--wait` plus the command's time well inside it. To queue for longer, wait in short steps without holding anything, then take the lock without waiting: `lock.py wait vita-build --wait 540` (exit 0 once it is free, 75 if not), then `lock.py run vita-build ... --wait 0 -- ...`, back to the wait if another job took it first (exit 75). `lock.py status` says who holds each lock and for how long.

The build's scenes and assets keep the scripts' fields as they were built, so `quickcode` stops when a type the data serializes changed (a field, a new MonoBehaviour or ScriptableObject) or a `[RuntimeInitializeOnLoadMethod]` came or went, and it warns when the asset rules or the build script changed since the full build. Those changes need `project` and `build` again (`--force` tries anyway).

For changes to assets, `pipeline.py build --scenes "Title,Station Square"` builds the first scene (Logos) and the named ones into `builds/crow-2018.2.19f1-vita-scenes`, leaving the full build alone; install it with `vita.py --build builds/crow-2018.2.19f1-vita-scenes install`. The game loads scenes by name, so loading a scene left out fails.
