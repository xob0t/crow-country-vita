# Status and plan

## The game

Crow Country is Unity 2022.3.49f1, Mono, built-in render pipeline, gamma colour space. Its data is 1.3 GB in 63 scenes. Most of the logic is PlayMaker FSMs (1,431 action classes) on top of SFB's own code in `com.sfbgames.*`. It also uses Rewired for input, DOTween, TextMeshPro 3, I2 Localization, ProBuilder and MeshCombineStudio, and Addressables for a few loads.

The data is heavy on 3D: 516,000 GameObjects, 86,000 meshes (412 MB of mesh objects), 130,000 mesh renderers and 239,000 MonoBehaviours. The largest scene file is 35 MB (Pool). Memory per scene will decide what runs on the Vita.

The game has a Switch build, and some of its code shows it. `CrowCountryCamEffect` has an `isSwitch` path that renders the camera at 624x351 instead of 1248x702.

## Done

- **Rip.** AssetRipper 2.0.0 exports the game as a 2018.2.19f1 project in about 4 minutes (92,809 assets, 2.7 GB). The first export stopped near the end with no error in either log; the second finished.
- **Code.** All 15 assemblies the game needs rewrite against the 2018.2 PS Vita engine with no unresolved references (`pipeline.py code`). The rewriter is The Drifter's core (retargeting, `RedirectMembers`, `Verify`) without its game-specific passes. CrowCompat fills in:
  - .NET Standard 2.1 string overloads, `TryGetComponent`, `Mesh.MarkModified`, `HasVertexAttribute`, `SetIndices(List)`, `LocalKeyword`, `Application.Quit(int)` and a few TMP needs (`compat/ApiShims.cs`).
  - TextCore's font data types under the field names 2022 serializes, so TMP 3's font assets load as written. FontEngine reports failure, so dynamic font assets get no new glyphs (`compat/TextCore.cs`).
  - Addressables. Unity.Addressables and Unity.ResourceManager are not shipped. The game's calls (`LoadAssetAsync`, `LoadSceneAsync`, `Acquire`, the operation handle) load from `Resources/Addressables/<key>` and `SceneManager` (`compat/Addressables.cs`).
  - VideoPlayer, which the Vita's 2018.2 player lacks (`compat/Video.cs`), on every platform. The game's videos are the health monitor loops (the status screen's `heartbeat Quad` in the player prefab, Pool, the Ending Sequence). `video_rules.py` decodes each webm with PyAV into a DXT1 atlas of half-size frames at 30 fps (2048x1024), a mono wav trimmed to the loop and a CrowCompat clip asset with the webm's GUID; CrowCompat's VideoPlayer blits the current frame into the target texture, loops, plays the sound on the target AudioSource and follows its time, on unscaled time (the status screen pauses the game). 10 clips, 304 frames; the player prefab carries about 5.6 MB of them. Checked on the Windows player; not yet on the console.
  - SFB's change to uGUI, `VertexHelper.SetUV1(Vector4)`. 2018.2 keeps uv1 as a Vector2, so the shim writes zw to uv2; `canvas_channel_overlay` adds the uv2 channel to the 14 canvases that pass uv1, and a shader rule (`VERTEX_INPUT_FIXES`) makes `Unlit/UIPixelate` read uv1.xy and uv2.xy. That shader draws the UI's pixel borders and highlights (about 1,000 elements in the player prefab: map, pause, status, dialogue, save/load; the menus' highlights). Checked on the Windows player (the status screen's box borders were missing); not yet on the console.
  - A rewriter pass, `RetypeFields`, converts TMP's stores to `UIVertex.uv0` (Vector4 in 2019+, Vector2 in 2018).
- **Shaders.** USCSandbox decompiles all 29 of the game's own shaders. It needed a fix for 2022: the player programs are stored one list per graphics tier, and it read the last list, which is empty (`patches/uscsandbox-tiers.patch`). It also wrote render state set from material properties as the properties' default values (`patches/uscsandbox-staterefs.patch`), so all TextMeshPro text, the whole main menu included, drew with `ColorMask 0`, and SFBStandard's and the particles' blend, ZWrite and cull modes ignored their materials. It now writes `ColorMask [_ColorMask]`, `Blend [_SrcBlend] [_DstBlend]` and so on, as the originals have them. `Standard` fails to decompile, but the game gets the 2018.2 built-in one.
- **First import.** The first editor import stopped on the I2 Localization targets. I2 keeps each `Localize` component's target object in the scene, and AssetRipper exported the 70 targets as assets that reference the scene's text components. Unity logged "Do not use ReadObjectThreaded on scene objects!" without end, 11.8 GB in 30 minutes. `scene_reference_overlay` now cuts asset references to scene objects; I2's `LocalizeTarget.IsValid` finds the same component again at run time. The editor's API updater also failed to check five rewritten assemblies (it couldn't resolve the engine modules their attribute enums come from). That was only logged, but the rewriter now marks every assembly with `[UnityAPICompatibilityVersion("2018.2.19f1")]`, so the updater skips them.
- **Material keywords.** Unity 2022 keeps keywords in `m_ValidKeywords`, and the export left every material's `m_ShaderKeywords` empty, so all 3,379 Standard materials would have lost their alpha modes, detail maps and emission. `material_rules.py` matches each exported material to the game's by name and property values (3,627 of 3,643 match) and writes the original keywords back. The few without a single match get what Unity's Standard inspector would set; that derivation agrees with the real keywords on 3,374 of the 3,376 matched Standard materials.
- **Vita shader compile.** Two decompiler outputs psp2cgc rejects. The light probe proxy volume uniforms are declared by Unity only where `UNITY_LIGHT_PROBE_PROXY_VOLUME` is on, which it isn't on the Vita, and the decompiler leaves Unity's uniforms undeclared (`conditional_uniforms` adds them under the opposite condition). A program's vertex and fragment variant blocks can both declare a uniform for the same variant (`guard_repeated_declarations` gives each repeated declaration its own `#ifndef` guard).
- **Linker.** `typeof()` in attribute arguments (`[CheckForComponent(typeof(VideoPlayer))]` on 11 PlayMaker actions) is stored as a name in the attribute blob, outside the type table, and kept pointing at the Vita's empty VideoModule. The rewriter now retargets those (82 sites) and Verify checks them. The game assembly also kept assembly references to the Addressables DLLs after all their types moved to CrowCompat; those are dropped.
- **Rewired and Mono 2018.** The first Windows player booted to the title, but Rewired failed to start ("Input will not function") and logged errors every frame. Three findings:
  - AssetRipper's exported DLLs are not the game's: its `Rewired_Core.dll` has an interface method the game's lacks, so a class implementing it failed to load (Mono), and IL2CPP refused to convert it. The rewriter now reads the game's own `Managed` folder; the export gives only the `.meta` GUIDs.
  - Rewired's obfuscated classes re-declare interfaces their base classes implement explicitly, which Mono 2018 can't resolve. `ReimplementedInterfaces` (`rewriter/Runtime.cs`) drops the re-declaration where the class implements nothing itself, and otherwise gives it explicit forwarding stubs.
  - The game's one default interface method (`IFsmStateActionGUI.OnGUI`, empty) becomes abstract; its implementers inherit `FsmStateAction.OnGUI`.
  - Compilers mark unsafe assemblies with security declarations that the 2018 class libraries can't resolve; Unity's linker stopped on them, so they're stripped.
- **Quick checks.** `pipeline.py link` runs Unity's linker on the rewritten assemblies (seconds, where the editor reports it after building every scene), and `pipeline.py loadcheck` loads every type and compiles every method under the editor's Mono in a copy of the Windows player.
- **First runs.** The Windows player boots to the title and loads Station Square from `-crow-scene` in about 3 s. There, about 900 of the scene's 6,073 renderers are enabled and about 306 visible, with 12-14 lights (2 directional, 8-10 point, 2 spot).
- **Project.** `pipeline.py project` assembles the 2018.2 project with the rewritten assemblies, decompiled shaders, Vita audio and texture import settings, the Addressables assets moved into Resources, the VideoPlayer components replaced by CrowCompat's, and the build script.

- **Vita build.** The editor builds the PS Vita player: IL2CPP for PSP2, 63 scenes, 1.5 GB of data. `pipeline.py package` makes `builds/crow-2018.2.19f1-vita.vpk` (535 MB, title ID CROW00001) with LiveArea art from the Steam store images (`livearea.py`): the booth crow as the bubble, the ticket booth scene as the background, the logo capsule as the gate and boot picture. On the console (`vita.py install`, `launch`, `shot`, `perf` with vitacompanion 1.35) it boots: the boot picture, the SFB Games logo at about 48 fps, then about a minute of black screen at 24 fps with one core at 98% while the title loads, then the title screen at 40 fps, GPU at 81%. The title showed keyboard prompts and didn't react to synthetic Cross or Down presses. `ProbeFiles` now writes the player's log to `ux0:data/crow/log.txt` (`vita.py log`) to find out why.
- **First console findings.** The log showed three problems the Windows Mono player hides:
  - Saves. `CrowCountrySave` keeps its slots in `Saves/` relative to the working directory, read-only app data on the console ("Access to the path "Saves" is denied"), and the PS Vita player's `persistentDataPath` (SmoothSave, I2) is empty. `compat/Saves.cs` puts both in `ux0:data/CrowCountry` there; the rewriter sends the `"Saves"` literals and every `persistentDataPath` read to it. Desktop players keep the game's paths.
  - BinaryFormatter. The game's data names `Assembly-CSharp`, which the port renames; Mono resolves it through `AssemblyResolve`, IL2CPP never asks. Every `new BinaryFormatter()` now starts with CrowCompat's alias binder (`TypeNames.NewBinaryFormatter`), and the title's save slot loads.
  - Input. Unity sees the pad (`PS Vita`, Cross = joystick button 0, d-pad 8-11) and Rewired assigns it to the player, but unmapped, so no button did anything and the prompts stayed keyboard ones (`KeyboardOrControllerCheck` turns to pad glyphs on a Rewired button). Rewired's `InputManager.DetectPlatform` is compiled into the game's firstpass assembly with the build's defines and says Windows, so Rewired matched the pad against the Windows entries of its controller database. Its PS Vita entry (`SonyPlaystationVita`, `fallback_PSVita`, product name "PS Vita") is there; `PatchRewiredPlatform` makes DetectPlatform answer PSVita and IL2CPP on the console (`compat/RewiredPlatform.cs`). The game picks PlayStation glyphs for a pad whose name has "sony" in it (`PMControllerType`).
  - Load time. The title appeared about 3 minutes after launch: two single frames took 41 s (Logos scene) and 61 s (loading Title). A `-crow-stall-dump 15` run (Diag crashes the player when a frame passes 15 s; `vita.py crashes --pull --thread main` symbolizes the main thread) caught it in `ResourceManager::FindDependencies`, recursing under `Resources.LoadAsync`: `MaraLoader.EarlyLoadMara` loads the player prefab (`CharacterCameraPrefab`) through Addressables, which CrowCompat served from Resources, and the player works out a Resources asset's dependencies at run time. The prefab now goes in a CrowCompat `AddressablesTable` in the player's preloaded assets (`DowngradeBuild.PreloadAddressables`), loaded at startup with the dependencies the build lists.
  - Shadows. With the game's High shadow resolution the player crashed on the render thread (`GfxDeviceGXM::Clear`) at the first frame with a shadow, in Driving Intro. Medium and Low work, soft and hard; the Vita project's quality level now has Medium (`PLATFORM_QUALITY_RULES`).
- **Setup and build.** `tools/setup.py` installs the editor and its PS Vita and IL2CPP modules, AssetRipper, Mono.Cecil, the .NET 8 SDK and the PS Vita SDK with its tools, with pinned hashes, and `setup.py doctor` checks them (all green on this machine; the installers themselves are untested). `build.py` runs setup and the stages in order under the build lock, skipping the rip while the export is current. [docs/build.md](build.md) and [docs/vita.md](vita.md) are the user docs.
- **On the console (evening).** The title appears about 45 s after launch (it was about 3 minutes); the remaining single-frame loads are Title (about 18 s: PlayMaker deserializes Title's 3,060 actions on the preload thread while the main thread waits, then the unused-asset unload walks the 73 MB managed heap) and Title → Driving Intro (about 40 s). Menus work with the pad and PlayStation glyphs from the first frame (`PatchKeyboardOrController`); console mode checks out (no Quit, no Screen entry). Settings save to `ux0:data/CrowCountry/Saves/save0.sav` and load after a restart. Rewired maps the Vita's L and R to the template's L2/R2, so aim and the page buttons (L1/R1) were out of reach; `rewired_vita_overlay` gives the game's maps Vita copies with them on L and R (untested in play). Driving Intro draws correctly at 17-18 fps. **Loading Roadside, the first playable scene, runs out of memory** (`InstantiateMara` copying the player prefab): nothing past the intro is playable yet.
- **Frame time on the console.** Driving Intro: 58-62 ms a frame (16-17 fps), CPU-bound in draw submission on the main thread (`FinishFrameRendering` 39-44 ms: culling 1.4, scene draw 35, post chain 2.5) and Unity's render worker (CPU 1; the 83-98% on CPU 2 is FMOD's mixer and the loading thread); scripts 11-12 ms. About 870 draws: base passes, 382 forward-add passes for 162 renderers at 4 pixel lights (Diag's drawAdd counted 638, an overestimate), shadow casters, screen-space shadow depth. Each lighting saving costs looks or little time: 1 pixel light + no shadows 45 ms (22 fps); shadows off alone saves 7.5 ms (the car's and walls' shadows go); 2 pixel lights lose Mansion's skull spotlight and candle glow; the dim second directional light per vertex darkens Driving Intro by about 22%. The game's lighting stays as it is. The Vita runs vSyncCount 2 (`CamEffect.cs`): a steady 30 fps on the title instead of 42 fps alternating 16.7/33.3 ms. Title: 23.7 ms, 7 ms of scripts. `Quality.cs` has the tools (`-crow-loop-profile`, `-crow-light-report`, `-crow-ab`, `-crow-census`, `-crow-disable`).
- **Load times.** Boot to title about 21 s (38-42 s before; about 3 minutes this afternoon); New Game → Driving Intro one 16.6 s frame (about 40 s); managed heap at Logos / Title 24.5 / 31.5 MB (65.8 / 73). Sampling the loading thread (`work/load-speed/scripts/loadprofile.py`) and stall dumps: PlayMaker builds each FSM's actions by reflection on the loading thread (30% of that `typeof()` lookups taking a lock, plus `TypeNames.GetType`, whose cache worked only on the main thread); cloning the player prefab (10,000 GameObjects, 8,000 behaviours) took a third of the first area load; the unused-asset unload after each load walks the managed heap (15-23%). `compat/Loading.cs`: the player prefab is an inactive instance in a scene of its own (`CrowMara`, scene 64, built by `DowngradeBuild`), loaded in the background on the title and taken by `MaraLoader` instead of a clone (`PatchMaraLoader`); Title is read during the logos (`ScenePrefetch`, `PatchLoadSceneAction`); `typeof()` in PlayMaker goes through a cached `TypeOf<T>` (`CacheTypeOf`, 302 sites); `TypeNames`' cache works on every thread. The preloaded table is empty now. Probe flags `-crow-load-trace`, `-crow-mcs-time`, `-crow-no-prefetch`. Shader data is 2.4 MB in all, so the duplicate shaders and deferred passes aren't worth removing.
- **Draws.** Draw count doesn't limit the frame: Driving Intro (about 700 draws: 162 base, ~380 additive, 160 shadow casters) stays at 53-57 ms with dynamic batching on (off in the Vita build, on in Windows; on Windows it cuts the caster pass 160 → 38 draws) or with 157 of 162 casters off. All casters off saves 9 ms, the same as shadows off: the shadow pass costs a fixed 9 ms, not per caster, and soft vs hard makes no difference. 4 → 1 pixel lights (about 260 fewer additive draws) saves 2 ms; the cost is the few full-coverage passes (ground, road), i.e. fill. With the clock test, the frame is GPU and memory bound. `compat/Draws.cs`: `-crow-draw-report`, `-crow-casters off|flat|small:<m>` (also `casters=` in `-crow-ab`). MeshRelease keeps the meshes of combiners that haven't combined yet (Gift Shop: 0 uncombined, was 10). The Vita compiles with `UNITY_NO_SCREENSPACE_SHADOWS`, but the decompiled `SFBStandard` and `ProBuilder/Standard Vertex Color` read shadows as the PC's screen-space path does, so their shadow receiving is probably wrong on the console (unchecked; most of the game uses the built-in Standard).
- **Station Square.** It loads and plays on the console (14.4-14.8 fps; Roadside → Station Square through the game's load path). It ran out of main memory: `-crow-memory-watch` (a sampler on its own thread, through long load frames) showed the old and new areas in memory together at the peak with CDRAM full of the old area's textures (the new ones went to main memory), then Boehm growing the GC heap by a third at once (91.6 → 122.1 MB) and aborting instead of collecting. `compat/Memory.cs`: the 26 MB PHYCONT pool, unused all along, backs the GC heap's sections (`PSVitaVideoPlayer.TransferMemToMonoHeap`); Boehm retries collections twice and grows by a sixth; a thread caps the heap so it leaves 16 MB to Unity; MeshRelease drops MeshCombineStudio's pooled buffers (~7 MB) and no longer touches Unity's built-in meshes. `compat/Loading.cs`: area loads go through an empty scene, freeing the old area and collecting first (about 3 s a load; `-crow-no-gap`); `RestartLevel` and `-crow-scene` use it; `-crow-scene-then <name> <s>` tests area-to-area loads. Station Square: 20-21 MB main memory and 7.4 MB CDRAM free, GC heap 122 MB (93.5 MB live; a full collection pauses about 1.15 s). Roadside now has 105-110 MB free (was 77). Pool still runs out: reading it takes main memory from 141 to 4 MB (137 MB of engine data), so it needs about 40 MB less texture, mesh and audio data; Ocean Kingdom, Haunted Hilltop and Underground NE are likely close.
- **GPU clock and camera size.** The GPU (166 MHz in power mode C) was the limit: in Roadside the main thread worked about 42 ms of each 63-67 ms frame and waited the rest, much of it in `ParticleSystemBeginUpdateAll` (4 systems, ~160 particles, no collision; stopping them saved nothing). The CrowClock plugin also sets the GPU clock (`scePowerSetGpuClockFrequency` 0x717DB06C, get 0x1B04A1D6, from vita-headers' ScePower.yml; `-crow-gpu-mhz`, default 222; the power mode resets it to 166 about 13 s in and the keeper restores it), and the camera renders 550x351 instead of 624x351 (`-crow-camera`), the width the effect's first pass reads, point-sampled, so the picture is the same. Roadside 63 → 46 ms (15.8 → 21.7 fps), Driving Intro 51 → 40 ms (19.6 → 25 fps); audio still keeps up. Not adopted: a 416-wide camera (another 3-4 ms, edges stair-step), Low shadow resolution (-2 ms), casters under 0.5 m off (-1.3 ms, debris loses shadows). Physics is cheap (6 rigidbodies, fixed step 0.02 s; a 1/30 step would slow Mara's walk ~7% through her drag). The frame is now bound by the main thread (~40-43 ms: draw submission ~25, scripts ~7.7, UpdateAllRenderers 2.7, the shadow pass's fixed ~7). `compat/Perf.cs`: `-crow-cycle`, `-crow-particles-report`, `-crow-physics-report`; `-crow-loop-cpu`.
- **Physics and controls.** Mara walks on the console with the D-pad and the left stick. Physics never ran in any port build: the game's DynamicsManager has `m_SimulationMode: 0` (step in FixedUpdate), which the 2018 export wrote as `m_AutoSimulation: 0`, and the game never calls `Physics.Simulate`; her walk is a PlayMaker AddForce on her rigidbody, so she turned but didn't move, and nothing fell or flew. `PHYSICS_RULES` sets it to 1 on every platform. Input itself works: Unity 2018 reports the left stick on its X/Y axes, the right on axes 4/5, the D-pad both as buttons 8-11 and as axes 6/7 (which Rewired's Vita map reads), Cross as button 0; player 0's Vita map gets every action. `-crow-input` now also logs raw axes, held buttons, Rewired's active elements and player 0's actions as they change; vitacompanion's `press left-stick X Y` moves the stick for tests. Checked in Roadside: D-pad and stick walk and turn her, Cross examines (the locked trunk), Circle backs out, R aims, debris settles. `-crow-scene` waits for the player's scene (it hung loading an area while CrowMara loaded), reaching Roadside about 66 s after launch. Physics-driven things (falling, thrown and fired objects) are untested.
- **Audio.** The title stuttered for 15-30 s and New Game and the Driving Intro crackled. `-crow-audio` logs the audio clock's advance against the wall clock, and the CrowClock plugin reads each thread's run time from the kernel (`native/clock/threads.c`). Unity's loading thread and FMOD's mixer, stream and file threads run on CPU 2 (the render worker is on CPU 1). With the player scene loading in the background at High priority, the mixer got 15% of CPU 2 instead of the 58% it needs, and audio ran at about 25% of real time. The game's reverb filters cost about 20% of CPU 2 each and keep running after their sound ends: five start at New Game, each crow call in the intro leaves one, and audio ran at 66% speed (the cutscene follows it: 132 s instead of 65). `compat/Audio.cs`: FilterGate runs each reverb only while its sound plays plus its decay, at most 3 at once (`-crow-reverb-max`, `-crow-audio-game` turns it off), and the loading thread moves to CPU 1, where the background load runs at Normal priority (the title keeps 30 fps). Audio now keeps up with real time on the title, at New Game, in the intro (about 65 s) and in Roadside; measured, not yet listened to. The build has every clip as HEVAG whatever format is asked (the 2018.2 PS Vita module encodes nothing else), cheap to decode.
- **Script cost.** `tools/downgrade/cpuprofile.py` samples the main thread of the vitalike player and names functions from the PDBs (`artifacts/cpuprofile/`). At Vita-like speed, Station Square / Mansion / Driving Intro: rendering 41 / 38 / 62%, PlayMaker actions 12.7 / 11 / 5.6%, PlayMaker bookkeeping 6.5 / 6.2 / 1.6%, `FullScreenColour`'s fade loop in OnGUI 5.3 / 5.1 / 1.2%, audio 4.8 / 6 / 3.2%. `compat/ScriptCost.cs` and `rewriter/ScriptCost.cs` skip work with no effect: an array stack for PlayMaker's FSM stack (its pop ran a reflection lookup), loop counts reset only for FSMs that entered a state, delayed events processed only for FSMs that have them, and the fade component off while no fade runs (`-crow-script-cost game` turns them off for A/B). Bookkeeping and fade together: 7.6% → 0.5% in Station Square; on the console, no difference in Title or Driving Intro, which are few-FSM or draw-bound.
- **CPU clock.** The user's console runs at 500 MHz (PSVshell), but from about 2 s after launch the player's startup (its power mode) set it back to 333 MHz. `libScePower_stub.a` has no clock functions; `tools/downgrade/native/clock/build.py` makes a stub for `scePowerSetArmClockFrequency` and `scePowerGetArmClockFrequency` from the 28-character `scePowerSetConfigurationMode` stub (name and NID replaced, `psp2snarl`) and builds `CrowClock.suprx` with the bootstrap module IL2CPP loads for a `[DllImport]` (`Media/Plugins/X.suprx` and `X.suprx.b.suprx`); `pipeline.py` copies both into the build after a Vita build and after quickcode. `compat/Clock.cs` sets 444 MHz at start and every 2 s if it drops (`-crow-cpu-mhz`, 0 for the power mode's 333); 500 fails with 0x802B0000. Measured: Driving Intro 54.4-55.4 ms at 333, 53.5-54.9 at 444 (about 2%), with CPU 2 at 96-98% either way (that was FMOD's mixer running the game's reverbs, see Audio, not the render worker); Title and Roadside the same. So the main thread's frame isn't bound by the CPU clock; the GPU or the memory bus is the likely limit, worth measuring again with the reverbs gated. Next: the GPU clock through the same plugin (`scePowerSetGpuClockFrequency`; NIDs to check).
- **Settings and console paths.** The game has no graphics quality, shadow, resolution, vsync or frame-rate option (every light uses the quality level's shadow resolution; `CrowCountryCamEffect.Awake` forces vsync on), so its options can't select the crashing High shadows. It has a console mode the PC build never sets: the PlayMaker global "Control Mode Console", which forces PlayStation prompts, hides Title→Quit and Graphics→Screen and makes the cursors skip them; `PatchConsoleMode` sets it to 1 on the Vita (`compat/Settings.cs`, `-crow-console` overrides). `PlatformSpecificAnimation` (926 infected-crow skin blobs in 16 areas) turns on per-frame scale tweens and keeps the meshes out of combining on PC; the Vita takes the Switch and PS4 choice, off (`PatchPlatformAnimation`, `-crow-platform-anim`). The fullscreen and resolution calls do nothing on the Vita. Not yet checked on the console.
- **IL2CPP audit.** Every name the scene data resolves at run time (264,824 PlayMaker actions of 203 types; 1,138 Set/GetProperty actions; FsmObject/FsmEnum type names) survives the Vita's UnityLinker, and IL2CPP 2018 generates the generic instantiations the game creates at run time. - **Memory.** Roadside, the first playable area, now loads and runs on the console through the game's flow (Title → Driving Intro → Roadside; 77 MB of main memory and 25 MB of video memory free, 16 fps); before, it ran out of memory every time. The rest is harmless: the `lut` array cap (the dither shader doesn't use it), three Bakery components missing in the original too, psp2cgc warnings in deferred passes the forward-rendered game never runs. Five shaders are built twice from identical copies, and the decompiled surface shaders keep deferred passes; both are candidates for less shader data.
- **Iteration.** The project stage reruns in about 1.5 minutes (it took about 10): `common.scan` caches per-file results in `work/scan-cache` by size and time (the name scan opened 46,000 native assets, slow when they weren't in the disk cache, Defender's scanning likely), `sync_tree` lists each side once and keeps files whose bytes match with their dates, and CrowCompat is recompiled only when its sources change, so the editor reimports nothing on a rerun. The Vita editor build is about 20 minutes, 70% of it building scenes; `pipeline.py build --scenes "Title,Station Square"` builds Logos and the named scenes into `builds/crow-2018.2.19f1-vita-scenes` for tests (scenes the game loads by name and that are left out fail to load). `pipeline.py quickcode` rebuilds only the code: it rewrites the assemblies and replays the last build's UnityLinker and IL2CPP command lines (from its log) on the inputs the build script saved (`work/vita-code-stage`), with IL2CPP's object cache, and puts `il2CppAssemblies.suprx` and `global-metadata.dat` in the build (about 2-4 minutes, then `vita.py sync`, about 1). It refuses when a serialized type's field layout or the start hooks differ from the build's (`SerializedLayout.cs`, `--force` to override) and warns when asset rules or the build script changed. `lock.py run` puts the command in a job object, so a killed run no longer leaves the editor running with the lock held. On the console, `-crow-scene` starts in a scene, and `Quality`'s flags try settings without a build.
- **Shader state.** All TextMeshPro text, the main menu included, was invisible on both players; see Shaders above.
